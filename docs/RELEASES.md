# Сборка и выпуск GeoTrace

Версия приложения, формат проекта и номер build независимы. Версия этого этапа — 1.1.0. Номер build берётся только из фактического `github.run_number` рабочего процесса Checks, в котором проверены нативные пакеты. Публикация выполняется отдельно и не меняет номер уже проверенных бинарных файлов. Не считайте его по числу коммитов и не используйте номер ещё не завершившегося запуска как подтверждение успешной сборки.

## Последовательность выпуска

1. Завершить функции, обновить руководство, описание возможностей и ограничения качества.
2. Проверить проект реальных листов и запустить `python tools/check_suite.py`.
3. Установить одинаковую версию в `pyproject.toml` и `src/geotrace/__init__.py`.
4. Сохранить изменения в Git и обновить `main`. Checks проверяет Windows x64, Mac Apple Silicon и Mac Intel.
5. После успешных тестов `tools/write_build_info.py` записывает реальный номер, SHA коммита, ссылку CI и время сборки.
6. `tools/build_desktop.py` собирает автономное приложение, запускает самопроверку и создаёт нативный установщик. В CI установщик устанавливается и повторно проверяется реальный исполняемый файл.
7. После всех платформ проверяются подготовленные и визуально просмотренные DOCX/PDF из `docs/release-1.1`. Контрольные суммы и хеши исходных текстов исключают публикацию устаревшего документа. Отдельный процесс Publish verified build проверяет результаты всех платформ, берёт готовые пакеты этого запуска, сверяет build/SHA и публикует их без повторной сборки. Документы в выпуске имеют разные латинские имена, чтобы GitHub не свёл кириллические названия к одному имени.

Сбой теста, упаковки или установленного приложения останавливает публикацию. Финальный номер — номер запуска с успешно проверенными пакетами всех трёх платформ. Ошибка передачи файлов на GitHub не меняет бинарные файлы: публикацию можно повторить отдельно после проверки хешей. Если требуется исправление уже опубликованного выпуска, увеличьте версию; существующие файлы выпуска не перезаписываются автоматически.

## Локальная проверка упаковки

Установите зависимости разработки и упаковки:

```sh
python -m pip install -e ".[dev,packaging]"
python -m pytest -q
```

Для официального локального повторения используйте подтверждённые номер и SHA из Checks при вызове `tools/write_build_info.py`, затем запустите `python tools/build_desktop.py`. Скрипт не создаёт установщик без метаданных реального build. Не маркируйте локально изменённые исходники чужим SHA. Для отдельной разработки упаковки можно собрать само приложение по `packaging/GeoTrace.spec`, но такая сборка без метаданных остаётся `dev` и не является официальным выпуском.

Windows требует NSIS, Mac использует `pkgbuild` и `productbuild`. Подпись платным сертификатом и нотариализация не выполняются. ARM-приложение получает техническую ad-hoc подпись упаковщика; она не удостоверяет издателя и не снимает системные предупреждения.

## Документация и диагностические файлы

Источники руководства и презентационного документа — `docs/USER_GUIDE.md` и `docs/PRESENTATION.md`. `tools/build_user_documents.py` создаёт DOCX; PDF получают рендерингом DOCX. При редактуре нужно просматривать страницы, включая таблицы и иллюстрации. В автономном приложении поставляется HTML-руководство для работы без сети.

`selfcheck-*` подтверждает сценарий собранного приложения; `installed-*` — его повторение из установки CI. В диагностике используются синтетические карты. Исходные TIFF и эталоны не добавляются в Git; руководство содержит иллюстрации проверенного проекта. Отдельные исследовательские веса и зависимости в штатный установщик не входят.
